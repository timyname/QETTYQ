## 1. Цель текущего прохода

Собрать существующие сценарии QETTYQ в одно mobile-first веб-приложение для пилота в Астане. Не превращать продукт в набор несвязанных макетов. Каждый экран обязан иметь вход, выход, состояние возврата и честный режим данных.

Визуальное направление: тёплый светлый editorial-интерфейс Astana-first, крупные 3:4 медиа, матовые белые поверхности, глубокий jade, один restrained lime action, мягкая глубина и liquid glass только поверх медиа или карты.

## 2. Неподвижные продуктовые контракты

1. Основной dock содержит ровно четыре пункта: `Для тебя`, `Поиск`, `Карта`, `Профиль`.
2. Настройки открываются шестерёнкой справа сверху и не занимают пункт dock.
3. `Поиск` объединяет прямой поиск и диалог с помощником; это не два конкурирующих раздела.
4. `Планы` открываются из профиля, карточки и готового маршрута, но не возвращаются в dock.
5. Один `candidateId` связывает ленту, карту, чат, детали, маршрут, сохранение и share.
6. `Неизвестно` никогда не преобразуется в ноль, `бесплатно`, `нет мест` или подтверждённый факт.
7. Свайп влево означает `Не сейчас`, а не вечный dislike. Undo должен вернуть последнюю реакцию.
8. Геолокация запрашивается только действием пользователя. Координаты не записываются в постоянную память.
9. Маршрут показывает `network` только после ответа провайдера. Линейная оценка маркируется `estimated`; при отсутствии расчёта ETA не показывается.
10. Любая карточка события содержит источник и состояние свежести. Демо, snapshot, live, fallback и LLM не смешиваются.
11. Организатор появляется только после объяснимого eligibility; создание события сохраняет локальный черновик и не изображает публикацию без backend/moderation.
12. Алматы — будущий город, не часть текущего покрытия пилота.

## 3. Порядок реализации

### Шаг 0 · Сохранить границы

- Не менять пользовательские экспортные файлы и текущую презентацию.
- Не переносить секреты в клиент, Git, логи и Site archive.
- Сначала проверять существующий компонент и данные; не дублировать shell, dock и типы.

### Шаг 1 · Нормализовать модель приложения

- Ввести единый тип экранов и разделить `primary tab`, `stack screen`, `overlay`.
- Сохранить контекст пользователя отдельно от текущего экрана: город, язык, время, бюджет, interest reactions, location permission, selected candidate, saved plans, local chat memory.
- Навигация dock меняет primary tab; карточка или CTA добавляет stack screen; close сначала закрывает overlay, затем back возвращает предыдущий stack state.

### Шаг 2 · Закрыть P0 сквозным сценарием

Путь: bootstrap → первый контакт → 15 свайпов → время → бюджет → геолокация/ручная точка → поиск → персональная лента → детали → карта → маршрут/план.

Обязательные состояния: загрузка памяти, восстановление повреждённой памяти, swipe right/left/undo, `нужно уточнить`, no results, provider unavailable.

### Шаг 3 · Собрать четыре основных раздела

- `Для тебя`: персональная лента и объяснение `почему это показано`.
- `Поиск`: пустой composer, уточнение, карточки результатов внутри чата.
- `Карта`: интерактивная карта, фильтры, выбранный кандидат, список и детали.
- `Профиль`: память, источники, приватность, сохранённые планы, entry в organizer flow.

### Шаг 4 · Добавить P1 без ложной готовности

- Кино: список и детали сеанса только с источником; без источника — честный posterless/demo state.
- Сохранённые планы и share: stale state, срок ссылки, privacy copy, system share/copy fallback.
- Организатор: eligibility → четыре шага формы → preview → локальный статус модерации → кабинет. Реальная публикация не имитируется.
- Алматы: informational locked state.

### Шаг 5 · Свести внешний публичный Site

- Публичный Site использует те же четыре пункта dock, названия, состояния неизвестности и модель локальной памяти.
- В Site не переносится server-only конфигурация и ключи.
- Интерактивность публичной версии должна покрывать тот же основной сценарий, даже если live API недоступен и включён маркированный deterministic fallback.

### Шаг 6 · Проверить

1. `typecheck`, `lint`, unit/integration tests.
2. E2E основного пути и переходов dock/back/overlay.
3. Мобильные размеры 390 × 844 и 430 × 932: нет горизонтального scroll, dock не перекрывает CTA.
4. Reduced motion, keyboard focus, screen-reader labels.
5. Ошибки карты, AI и источников не блокируют ручной fallback.
6. Проверка отсутствия секретов в bundle/archive.
7. Production build root app и Site checkout.

### Шаг 7 · Опубликовать

- Получить текущий Site и сохранить его audience.
- Открыть source через официальный Site workflow, внести проверенную версию, собрать archive.
- Сохранить новую версию и развернуть в существующий Site, не создавая дубликат.
- Дождаться terminal deployment status и открыть буквальный URL.

## 4. Критерий завершения

Проход завершён только если пользователь может пройти основной сценарий, открыть все четыре раздела, вернуться назад без потери контекста, увидеть честные fallback-состояния, сохранить/удалить локальную память и получить работающий публичный URL. Наличие 44 описанных artboard само по себе не считается готовым приложением.
