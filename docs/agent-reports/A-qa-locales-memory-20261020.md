## Реальный HTTP + VPS/SQLite integration, 21 октября

В том же отдельном QA-spec Node HTTP-сервер слушает **только `127.0.0.1`**, свободный порт выбирается ОС (`port=0`). Он вызывает настоящие route handlers `/api/session`, `/api/memory`, `/api/memory/consents`, `/api/memory/profile`, `/api/memory/messages`; инициализируется настоящий `initializeVpsRuntime`. SQLite находится в test-owned `mkdtemp` каталоге. Передан explicit env с `NODE_ENV=test` и `QETTYQ_DATABASE_PATH`, без копирования process env или чтения `.env`. Источник событий — локальный существующий snapshot. Никаких provider requests.

Проверено фактически:

- До opt-in GET возвращает `enabled:false`, пустую память и **не** устанавливает memory-cookie; запись профиля без identity — 409.
- Opt-in выдаёт HttpOnly cookie; профиль сохраняется. Запись диалога без отдельного разрешения — 403.
- После 28 сообщений восстанавливаются ровно последние 24, с правильными первым/последним сообщением.
- HTTP listener, runtime и DB полностью закрываются и открываются заново на том же SQLite-файле. Старый guest session — 401; новый session создаётся, а сохранённый memory-cookie восстанавливает профиль и историю. История помечена `untrusted_personal_context`.
- Чужой cookie jar и угаданный memory-cookie не открывают чужую память.
- Cross-site DELETE — 403; после него все 24 сообщения остаются.
- Отзыв dialogue удаляет сообщения, но не профиль и его consent.
- Полное DELETE очищает память, возвращает `deleted:true`, удаляет HttpOnly cookie через `Max-Age=0`; следующий GET опять `enabled:false`.

После теста HTTP listener закрыт, runtime/DB закрыты, удалён только созданный тестом временный каталог. Основной dev-сервер 3000 и пользовательские данные не затронуты.
